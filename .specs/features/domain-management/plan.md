# Managed domains: automatic, scoped updates

## Problem

The tray only reads the configured allowlist. The owner wants to add and remove public domains from Settings, including non-social domains, without administering the server for each change. Today `run` captures `config.domains` at start and Chrome uses a separately installed PAC. A successful config write or a `connected` status alone proves neither side has applied the new list.

## Flow

1. In Domains, a human requests one add or remove. The UI shows validation and pending/failed/applied states without implying live routing changed early.
2. The CLI remains the owner of hostname validation, the local allowlist and synchronization. The tray invokes typed operations, never arbitrary SSH, file paths or commands.
3. A separate server authority accepts only structured domain operations and renders its own fixed PAC. No production rollout is in scope. Chrome publication and local activation ordering are gated on the technical evidence below.

## Impact

- Tunnel runtime: one long-lived restricted forwarding connection, unchanged for unenrolled configs. No change to live SSH, keys or policy during development.
- Settings: existing Domains tab gains Add/Remove; no new listener, filesystem access from the webview or unrelated redesign.
- VPS: one protected policy and browser context, enabled only after one-time administrator enrollment and separately authorized rollout.

## Relations

| Entity | Relationship |
| --- | --- |
| Edit credential | Separate from the tunnel key; revocable by the VPS administrator; cannot open a shell or a forward. |
| Domain list | Validated at both boundaries; a proposed edit and an applied revision are distinct. |
| PAC | Generated by the server from validated domain data and the provisioned proxy address, never supplied as script by the Mac. |
| Live proxy | Enforces its own allowlist and network address restrictions regardless of PAC behavior. |
| Runtime receipt principal | A separate enrolled identity held by the upgraded proxy; the edit principal cannot use it or attest on its behalf. Root compromise of the Mac can also steal this authority; it still has no VPS shell or forwarding authority. |
| Edit operation | Immutable intent keyed by enrollment, operation ID and expected revision; one durable owner until terminal reconciliation. |

## Landing

| Decision | Status and scope |
| --- | --- |
| 1. Automatic restricted editing | Approved; initial VPS provisioning by the administrator once, not per domain edit. |
| 2. No admin credential on the Mac | Separate revocable SSH edit identity; fixed no-shell/no-forwarding operation. One administrator-installed, scoped publisher validates domain data and replaces only the enrolled mandatory `ProxySettings` policy, using a distinct inline PAC URL for each revision. No uploaded script or mutable PAC HTTP listener. |
| 3. Publication and activation | Durable publication, upgraded local proxy acknowledgement, and route proof in each enrolled Chrome context are distinct. The enrolled server-side runner explicitly reloads the policy, waits for the expected mandatory policy/digest, then proves current and wrong revisions through fresh route witnesses from the same browser generation. Never expose browser control to the edit identity. Start with one explicitly enrolled regular-profile browser context per managed policy; other contexts are not claimed. |
| 4. Local revocation | An upgraded `run` applies a bounded atomic domain-only snapshot without reopening the SSH tunnel. Acknowledgement follows removal of effective access, including in-flight or established relays; a parent that still covers the requested host is not revoked. Legacy configs stay unchanged until a separately authorized rollout. |
| 5. Transition semantics | Apply the home-side change before publishing Chrome policy; a stale PAC on removal still points to the now-denying proxy. A pending addition is not yet selected in Chrome and may use its former route; existing selected domains keep their proxy-only rule. Only mark applied after both acknowledgements. Strict no-direct from submission would require a separate browser traffic fence, outside this proposal. |
| 6. Publication authority and operation ownership | Claim durable same-enrollment single-flight before local mutation. The publisher authenticates the enrolled proxy's matching current-generation receipt independently of the edit identity. Disable/re-enrollment fences authenticated sessions and queued work by epoch at the mutation and publication barriers. |
| 7. Readiness and application scope | Verify exclusive mandatory policy ownership and isolation of its runner/profile, observer and proxy endpoint, and a matching live baseline before edits. Applied only covers fresh route decisions in that verified browser context, not already-open direct sessions or other profiles. |
| 8. Revocation recovery | A fenced operation with proof of no side effects becomes terminal `cancelled`. A fenced operation with applied, published or uncertain side effects becomes `recovery_required`. Only the provisioned VPS administrator, locally on that server, may authorize a forward recovery under a fresh epoch. Recovery uses the same bounded policy, independent live-proxy receipt and browser proof barriers. It never replays the fenced intent or re-allows hosts whose access was revoked. |
| 9. Legacy adoption preflight | The Linux administrator can check the existing fixed `agentes-meta-proxy.json` against a supplied Mac hostname list without writing files, starting a browser or granting edit authority. Exact mandatory legacy PAC dialect, matching public hostname set and no competing policy are required; unknown scripts are not executed. Success reports parity only, never readiness. |
| 10. Idle hold across forward recovery | An effect-uncertain operation keeps its original durable host hold when Disable fences the old epoch. A fresh, administrator-authorized recovery must bind its own revision and PAC preimage to that original hold. A replacement or unrecorded origin cannot grant effects. Reject clearing the old cohort to acquire a new one while effects remain uncertain. |
| 11. Applied idle-window reconciliation | Publish a durable root-local terminal receipt only when the guarded publisher finalizes. Bind it to the held ID and `sha256(JSON.stringify(["domains-idle-window-v1", enrollment, epoch, operationId, revision, domainsDigest, policyPreimageDigest]))` of the original operation, including after forward recovery. Do not expose this receipt to editor/proxy ingress or derive it from history alone. |
| 12. Idle-window preparation | The root-local publisher can read one claimed scope and its recognized PAC preimage even before a browser cohort is ready. The result cannot grant effects. Do not read the claim through the remote editor or treat an enabled epoch, an ordinary CDP endpoint, or a cached PAC digest as preparation authority. |
| 13. Root-local handoff reads | Reuse the Linux supervisor's private admin socket for exact `idle-candidate` and `idle-completed` reads. Do not introduce a login, a new listener, any role command, or a transport that can itself grant or release a window. |
| 14. Runner-side handoff reads | The Linux root host connects only to the fixed private publisher socket after checking every path component. Verify the bounded response against the configured enrollment, exact canonical digest and original recovery scope; ambiguity is unavailable, not completion. |
| 15. Claimed-operation preparation | The root host reads the candidate, holds the exact enrolled children and rereads the same claim before durable arm. It returns a prepared binding only after exact server held readback and another unchanged claim read. Before arm, release a mismatched attempt; after arm, require terminal reconciliation even if a later read is missing. Do not start a new hold for a recovery claim or treat any of these reads as Chrome proof. |
| 16. Cold completion on the same Linux host | Persist the native machine and boot IDs in newly armed server-fenced journals. Automatic cold reconciliation requires an exact publisher terminal receipt and the same machine ID with a different kernel boot ID; an empty process map, daemon restart, different host or legacy record is not absence proof. This relies on single-host native storage and does not authorize clearing a journal copied to another machine or VM clone. |
| 17. Explicit no-effect cancellation | The root-local administrator may cancel one exact ordinary `claimed` operation using its enrollment, hold ID and candidate digest. The publisher checks the current PAC preimage and atomically retires that intent and publishes a terminal receipt, without changing the PAC or granting a home mutation. Do not cancel on a busy status or timeout. Once the activation CAS has won, or if the claim is missing, stale or a recovery, refuse; use terminal evidence, not absence, to release a durable hold. |

## Criteria

**Acceptance Criteria**

1. WHEN a user edits Domains THEN the system SHALL add or remove canonical public DNS names including non-social domains; reject URLs, IPs, wildcards, public/shared suffixes and reserved proof names; detect normalized repeats; distinguish parent-covered removals; and accept empty managed lists as deny-all.
2. WHILE independent local and every enrolled browser acknowledgement are missing THEN the system SHALL report pending or unknown, not Applied. Unmanaged installs SHALL report setup required and write nothing.
3. WHEN the edit identity authenticates THEN it SHALL only read the enrolled revision and submit bounded typed hostname edits. It SHALL deny shell, TTY, arbitrary execution, forwarding, uploads and other files; expose no administrator credential, tunnel key, user browser credential or browser control.
4. WHEN an edit is attempted THEN the system SHALL retain the checked-public-IP and port-443 proxy guards, render only the fixed PAC and proxy endpoint, reject invalid/stale writes, and allow one winning revision at a time.
5. WHEN verification runs THEN it SHALL use disposable configs, loopback fixtures and non-production Chrome/OpenSSH without any live tunnel, VPS or login change.
6. WHEN the matching live proxy acknowledges a revision THEN new matches SHALL be active and removed effective matches SHALL have no outstanding DNS/dials or relays. Unchanged and still-covered paths SHALL remain on the same SSH forward.
7. WHEN publishing a policy THEN the system SHALL require local activation first. Already selected routes SHALL never fall back to `DIRECT`; pending additions may retain the old route. Removal SHALL not publish direct routing without local denial. An interrupted request SHALL reconcile by operation ID/revision without repeating the edit or advancing observed revision.
8. WHEN proving browser activation THEN the observer SHALL explicitly reload, match mandatory policy/digest, and provide current and wrong-epoch route witnesses from that same instance/context. Enrollment and generation changes SHALL require fresh proof.
9. WHEN preparing a local mutation THEN the system SHALL first durably claim one immutable intent per enrollment. Publication SHALL require a separately authenticated current-proxy receipt matching enrollment, epoch, operation, revision and digest. Missing, edit-signed, forged, wrong-scope or stale receipts SHALL do nothing. Whole-list and request limits SHALL apply; key disable SHALL fence authenticated sessions and queued work.
10. WHEN interrupted or revoked THEN the system SHALL reconcile durable state without promoting stale evidence. A proven no-effect intent becomes terminal `cancelled`; applied/published/unknown effects freeze normal edits as `recovery_required`. Only a local VPS administrator SHALL authorize a higher revision in a fresh epoch. Preserve last-proven evidence separately, apply no broader a home list or restore revoked/uncertain access, and require current independent proxy/browser proof before marking the old intent terminal `reconciled` and releasing the claim. Retain the mandatory PAC for uncertain destinations until the administrator explicitly chooses their disposition; deliberate removal SHALL still meet the local-deny and publication barriers before `DIRECT`.
11. WHERE an enrollment is not proven exclusive, protected, and matched to an upgraded proxy and browser baseline THEN editing SHALL be disabled. An unrelated/lost/replaced observer SHALL report activation unknown, not Applied. Fresh nonce-bound route evidence SHALL distinguish positive, negative, proxy-down and wrong-context outcomes.
12. WHEN using Settings or CLI to edit domains THEN the system SHALL follow [dx.md](dx.md) and [uiux.md](uiux.md), including narrow IPC scopes, typed errors, repeatable Retry, absent vs verified-empty and truthful tray summaries.

## Assumptions

| Assumption | Resolution |
| --- | --- |
| One-time server enrollment | Expected for automatic operation; server operator identity and exact host policy are not assumed for any real deployment. |
